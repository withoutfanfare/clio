## User
Wire up Royal Mail tracking for dispatched orders. Their API docs are attached to the ticket.

## Assistant
Implemented. A scheduled command polls the Royal Mail Tracking API v2 for every order in the `dispatched` state and stores scan events on the shipment record. Two things came out of testing worth knowing: the API rejects any request whose tracking-number query batch exceeds 30 numbers (HTTP 400, undocumented — their docs claim 100), so the poller chunks at 30; and their rate limiter returns 429 with a Retry-After header that must be honoured or the key gets suspended for an hour.

## User
Good find on the batch limit. Which queue should the poller run on — I don't want it competing with artwork processing.

## Assistant
I've put it on the default queue, not `media`: the poll is I/O-light and quick, while `media` carries the heavy artwork jobs. If it ever grows, a dedicated `shipping` queue is the next step, but that's speculative today.

## User
Agreed, default queue is the right call — decision made. Anything left undone?

## Assistant
Two deliberate gaps: no webhook ingestion (Royal Mail's webhook programme needs a separate commercial agreement), and scan events older than the shipment's delivered date are not backfilled. The poller, chunking, 429 handling and event storage are all live behind the feature flag `shipping.tracking_enabled`.
